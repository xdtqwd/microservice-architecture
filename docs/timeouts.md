# Таймауты: иерархия и бюджет

Правило: внешний предел больше суммы внутренних. Иначе внешний срабатывает
раньше, чем внутренняя операция успеет завершиться или честно отказать.

## Запрос клиента

    http.Server.ReadHeaderTimeout   5s   заголовки от клиента
    http.Server.ReadTimeout        10s   весь запрос от клиента
    http.Server.WriteTimeout       15s   > дедлайна запроса: ответ успевает уйти
    └─ middleware Timeout          10s   дедлайн в ctx запроса
       ├─ ожидание соединения       1s   DB_ACQUIRE_TIMEOUT (AcquireTracer)
       ├─ лидер singleflight, товар 3s   leaderTimeout, на Background
       ├─ лидер singleflight, заказ 5s   createLeaderTimeout, на Background
       ├─ Redis                   0.1s   Dial/Read/WriteTimeout, без ретраев
       └─ Commit / Rollback         2s   txm.Detached(), не связан с запросом

Сумма худшего пути заказа: 1s (пул) + 5s (лидер) ≈ 6s < 10s.
Сумма худшего пути товара: 0.1s (Redis) + 3s (лидер) < 10s.

## Фоновые и служебные

    остановка сервера              12s   > дедлайна запроса: SIGTERM не обрывает
                                         запросы, которые ещё успеют завершиться
    /readyz, каждая зависимость   1.5s   параллельно, у каждой свой предел
    пачка релея outbox             15s   запись в Kafka по умолчанию ждёт до 10s
    перенос в DLQ                   2s   txm.Detached()
    подключение к Postgres          5s   ConnectTimeout

## Где context.Background() — и почему

| Место | Зачем Background | Предел |
|---|---|---|
| лидер singleflight (товар, заказ) | отмена одного клиента не должна убивать работу для всех ждущих | 3s / 5s |
| Commit / Rollback | на отменённом ctx pgx не отправит команду | 2s |
| инвалидация кеша | ctx запроса может быть уже отменён, а сбросить кеш нужно | Redis 100ms |
| перенос в DLQ | фоновая операция | 2s |

## Что было не так

1. **Middleware Timeout сам ничего не прерывает.** Он только ставит дедлайн
   в ctx. Работа останавливается там, где код сам смотрит в ctx: pgx, go-redis,
   select по ctx.Done(). singleflight.Do ctx не смотрит — клиент висел, пока
   лидер не закончит. Заменено на DoChan + select.
2. **WriteTimeout не останавливает хендлер.** Он запрещает писать ответ после
   срока. Хендлер доработал до 28-й секунды и получил обрыв вместо ответа.
3. **Запросы идемпотентности шли мимо транзакции** через r.pool на
   Background: ключ коммитился раньше заказа, а один запрос занимал два
   соединения. Перенесены в транзакцию через r.querier(ctx).
4. **Остановка ждала 5s при дедлайне запроса 10s** — SIGTERM обрывал
   живые запросы.

## Проверка

Таблица products под LOCK ... ACCESS EXCLUSIVE на 30s, кеши сброшены:
было — обрыв соединения через 28s, запрос в базе висел до снятия блокировки;
стало — 503 через 3.0s, запрос в базе отменён, соединение вернулось в пул.
