# RPC-03 · Дедлайны через границу сервисов

## Иерархия бюджета

    HTTP-сервер, WriteTimeout                 15s   ответ успевает уйти
    └─ дедлайн запроса (middleware Timeout)   10s
       └─ вызов каталога (order-service)      min(CATALOG_TIMEOUT 500ms, осталось − резерв 300ms)
          │                                   если вышло меньше 20ms — не звоним вовсе
          └─ grpc-timeout в заголовке         дедлайн едет на сервер уже урезанным
             └─ product-service, ctx вызова
                ├─ захват соединения из пула  тот же ctx
                └─ запрос в Postgres          тот же ctx: отмена -> CancelRequest в базу

Резерв — время, которое запросу нужно после ответа соседа: транзакция
заказа и ответ клиенту. Его соседу не отдаём.

## Эксперимент: база соседа отвечает 5 с, клиент ждёт 1 с

| | Сервер глухой к отмене | Сервер слушает ctx |
|---|---|---|
| ответ клиенту | 503 за 1.007 с | 503 за 1.005 с |
| pg_sleep в базе после ухода клиента | 1 — ещё работает | 0 — отменён |
| сервер проработал | 5.023 с | 0.999 с |
| метрика сервера | outcome="wasted" | outcome="abandoned" |

Для клиента разницы нет. Глухой сервер четыре секунды держал соединение
и запрос в базе ради ответа, который никто не ждал.

Сервер видит `context canceled`, а не `deadline exceeded`: клиент сам
обрывает вызов по своему дедлайну. Реагировать нужно на любое завершение ctx.

## Метрики

- `rpc_client_deadline_total{method, code}` — order-service: вызовы,
  оборванные дедлайном или отменой
- `rpc_client_skipped_total{method}` — вызовы, которые не делали:
  бюджета уже не хватало
- `rpc_server_client_gone_total{method, outcome}` — product-service:
  `abandoned` — бросил работу вслед за клиентом, `wasted` — доделал впустую.
  Рост `wasted` — сигнал, что где-то контекст не доезжает до работы.

Проверка: `load-tests/rpc/deadlines.sh`.
