# MQ-07 · Воспроизведение рассинхрона между Postgres и Kafka

## Сценарий 1 — заказ есть, события нет

### Как воспроизводил

В `order_service.go` добавил `panic` после `tx.Commit()` и до отправки в Kafka:

```go
tx.Commit()
panic("killed after commit, before kafka send") // точка убийства
producer.SendOrderCreated(ctx, orderID)
```

Запустил сервис, создал заказ:

```bash
curl -X POST http://localhost:8083/orders \
    -H "Content-Type: application/json" \
    -d '[{"product_id":1,"quantity":1}]'
```

### Что оказалось

```sql
SELECT id, status FROM orders ORDER BY id DESC LIMIT 1;
-- id=10033353, status=pending  ← заказ есть
```

```bash
kafka-console-consumer.sh --topic orders --from-beginning --max-messages 10
# вывод пуст ← события нет
```

### Итог

Заказ в базе существует, потребители никогда не узнают о нём.
Покупатель оплатил, но склад не списал остаток, письмо не отправлено.

## Сценарий 2 — событие есть, заказа нет

### Как воспроизводил

Переставил порядок: сначала `producer.Send`, потом `tx.Commit()`.
Сымитировал откат — создал заказ с несуществующим product_id:

```go
producer.SendOrderCreated(ctx, orderID) // событие ушло
tx.Commit()                             // завершится ошибкой если CHECK нарушен
```

```bash
curl -X POST http://localhost:8083/orders \
    -H "Content-Type: application/json" \
    -d '[{"product_id":99999,"quantity":1}]'
```

### Что оказалось

```sql
SELECT id FROM orders WHERE id = <last_id>;
-- 0 rows ← заказа нет, транзакция откатилась
```

```bash
kafka-console-consumer.sh --topic orders --from-beginning
# {"order_id": <last_id>} ← событие есть
```

### Итог

Потребитель получил событие `order_created` для заказа которого нет в базе.
Попытка обработать его приведёт к ошибке или фантомному списанию остатка.

---

## Почему перестановка порядка не помогает

| Порядок | Поломка |
|---------|---------|
| commit → send | заказ есть, события нет |
| send → commit | событие есть, заказа нет |

Это не баг реализации — это фундаментальная проблема двух независимых систем.
Любой порядок оставляет окно между двумя операциями где процесс может упасть.

---

## Почему двухфазный коммит не вариант

Kafka не поддерживает XA-протокол — у неё нет операции `prepare`.
Встроить её в 2PC физически невозможно.

Даже если бы поддерживала — 2PC блокирует ресурсы между фазами.
Координатор упал между `prepare` и `commit` — транзакция висит заблокированной
до таймаута или ручного вмешательства. На нагрузке это убивает систему.

---

## Что даёт outbox

Outbox не убирает потерю событий — он заменяет её на at-least-once доставку.

**До outbox:** событие может потеряться навсегда (сценарий 1).

**После outbox:** событие гарантированно доедет, но может приехать дважды
(при падении relay после отправки но до простановки `published_at`).

Потребитель обязан быть идемпотентным — именно для этого inbox в MQ-06.

Таким образом: outbox + inbox = exactly-once семантика на уровне приложения,
без распределённых транзакций.
